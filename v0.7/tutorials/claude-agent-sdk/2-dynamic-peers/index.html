    Tutorial: A Claude Supervisor That Discovers Its Workers¶

    In this tutorial you build a travel-planning supervisor with the Claude Agent SDK whose workers are not named in its code. At startup it asks Kynomesh who its workers are, reads what each one can do, and generates one tool per worker. The workers are Claude agents too.

    Add or remove a worker in the AgentSet and the supervisor picks it up, with no code change and no new image.

    flowchart LR
    client([Client]) -- A2A --> supervisor
    subgraph set ["AgentSet: claude-travel"]
        supervisor -- A2A --> flights
        supervisor -- A2A --> hotels
        supervisor -. A2A .-> weather["weather<br/>(added and removed in this tutorial)"]
    end

    This tutorial builds on Single agent, which explains the executor, the AgentCard and how a Claude agent is locked down for a pod. The discovery idea is the same as in the LangGraph version; this page shows how it looks with Claude tools. The full example is in kynoproj/kynomesh-examples.

    git clone https://github.com/kynoproj/kynomesh-examples.git
cd kynomesh-examples/claude-agent-sdk/dynamic-peers

    What's in the Example¶

    File Purpose
    src/claude_travel/discovery.py Finds the supervisor's workers and reads each one's AgentCard.
    src/claude_travel/supervisor.py Builds one tool per worker, and the prompt's worker list, from those cards.
    src/claude_travel/agent.py The Claude setup shared by every role, including the lock-down options.
    src/claude_travel/workers.py The worker roles the image can run: flights, hotels and weather.
    src/claude_travel/main.py Starts the supervisor or a worker. --role picks which.
    manifests/agentset.yaml The supervisor, flights and hotels.
    manifests/agentset-with-weather.yaml The same, plus weather.

    The workers use stub tools with canned data, so the example needs no travel API.

    How Discovery Works¶

    An agent's AgentCard describes what it is and what it can do. Each worker already publishes one, so the supervisor learns about its workers by reading their cards instead of being told about them.

    discovery.py lists the supervisor's peers, then reads each peer's card:

    async def discover_workers() -> tuple[WorkerInfo, ...]:
    workers = []
    for name in sorted(client.peers()):
        card = await client.resolve_agent_card(name)
        workers.append(WorkerInfo(
            name=name,
            description=card.description,
            skills=tuple((s.name, s.description) for s in card.skills),
        ))
    return tuple(workers)

    client.peers() returns the agents the supervisor may call, and client.resolve_agent_card(name) returns a peer's card. Nothing here names a worker. The version in the example also retries an unreachable worker a few times, then logs and skips it so one slow worker does not stop the supervisor from starting. For the general technique, see Discovering Peers Dynamically.

    Building Tools from Cards¶

    supervisor.py turns each discovered worker into a Claude Agent SDK tool. The tool's description comes from the worker's card, and calling it sends the request to that worker over A2A:

    def peer_tools(workers, ask_peer):
    def make(worker):
        async def delegate(args):
            try:
                return text_result(await ask_peer(worker.name, args["request"]))
            except Exception as e:  # the model should see a failed worker, not crash the run
                return error_result(f"Error: worker {worker.name!r} failed: {e}")

        return tool(tool_name(worker.name), describe(worker), {"request": str})(delegate)

    return [make(w) for w in workers]

    If a worker fails, the tool returns the error to Claude instead of raising. The supervisor can then answer around the failure rather than crash the run.

    The prompt lists the workers the same way, one line per worker:

    You are a travel-planning supervisor. ...
Your workers:
- ask_flights: Finds flights between cities. Skills: Search flights: Flight options with times and prices.
- ask_hotels: Finds hotels in a city. Skills: Search hotels: Hotel options with nightly prices.

    Both the tool list and the prompt are passed to the shared lock-down helper, so the supervisor can use only its worker tools, and none of Claude's built-in tools:

    def supervisor_options(workers, ask_peer) -> ClaudeAgentOptions:
    return locked_down_options(
        system_prompt=build_prompt(workers),
        tools=peer_tools(workers, ask_peer),
    )

    Because Claude chooses tools from these descriptions, the quality of a worker's AgentCard matters. A clear description and skills are what let the supervisor route requests correctly. If a request needs a worker that does not exist, the prompt tells the supervisor to say so plainly.

    The AgentSet¶

    The base manifest deploys the supervisor with flights and hotels, and turns on driftReload:

    apiVersion: kynomesh.kyno.sh/v1alpha1
kind: AgentSet
metadata:
  name: claude-travel
spec:
  pattern: Supervisor
  entry: supervisor
  driftReload:
    enabled: true
  agents:
    - name: supervisor
      container:
        image: claude-travel:latest
        imagePullPolicy: IfNotPresent
        args: ["--role", "supervisor"]
        env: &anthropic-env
          - name: ANTHROPIC_API_KEY
            valueFrom:
              secretKeyRef:
                name: anthropic-api-key
                key: ANTHROPIC_API_KEY
    - name: flights
      container:
        image: claude-travel:latest
        imagePullPolicy: IfNotPresent
        args: ["--role", "flights"]
        env: *anthropic-env
    - name: hotels
      container:
        image: claude-travel:latest
        imagePullPolicy: IfNotPresent
        args: ["--role", "hotels"]
        env: *anthropic-env

    pattern: Supervisor lets the supervisor see every other agent, which is what client.peers() returns. driftReload is explained below.

    Run the Tests¶

    uv run pytest

    The tests make no API calls. The supervisor only runs on Kynomesh, while a worker runs locally:

    ANTHROPIC_API_KEY=... uv run python -m claude_travel.main --role flights

    Deploy to Kynomesh¶

    make build
# kind:  kind load docker-image claude-travel:latest
# k3d:   k3d image import claude-travel:latest -c <cluster>
kubectl create secret generic anthropic-api-key --from-literal=ANTHROPIC_API_KEY=...
make deploy
kubectl get agentset,agentdeploy
kubectl port-forward svc/claude-travel-ingress 8490

    The supervisor logs the workers it found at startup:

    kubectl logs -l app.kubernetes.io/name=claude-travel-supervisor -c agent | grep discovered

    Ask it to plan a trip, then ask for something it has no worker for yet:

    a2acli -k -u https://localhost:8490 --override-host=localhost:8490 \
  send 'Plan a weekend in Tokyo: flights from SFO and a hotel'

a2acli -k -u https://localhost:8490 --override-host=localhost:8490 \
  send 'What is the weather in Tokyo this weekend?'

    The first question is answered using the flights and hotels workers. For the second, the supervisor tells you it has no worker that can help. Each request starts the Claude Code CLI in every agent involved, so allow some time for the reply.

    Add a Worker with No Code Change¶

    Apply the manifest that adds the weather worker:

    kubectl apply -f manifests/agentset-with-weather.yaml
kubectl get pods -w

    The new weather pod starts, and the supervisor's pod restarts. Kynomesh restarts it because its set of workers changed, and on startup it discovers all three:

    kubectl logs -l app.kubernetes.io/name=claude-travel-supervisor -c agent | grep discovered

    Ask the weather question again. It is now answered:

    a2acli -k -u https://localhost:8490 --override-host=localhost:8490 \
  send 'What is the weather in Tokyo this weekend?'

    The two manifests differ only by the added weather agent. The supervisor's code and image are identical. To remove the worker, apply the base manifest again and the supervisor goes back to two workers:

    kubectl apply -f manifests/agentset.yaml

    Change a Worker's Card: Drift Reload¶

    The supervisor reads each worker's card once, at startup, and builds its tools and prompt from it. If a worker later gains a skill, the supervisor would keep describing it the old way until something restarted it.

    driftReload closes that gap. When a worker's AgentCard changes, Kynomesh restarts the agents still holding the stale copy, so the supervisor rebuilds its tools from the new card.

    To try it, the workers read an optional EXTRA_SKILLS environment variable that adds skills to their card. It stands in for shipping a new version of an agent that gained a skill. Add one to hotels:

    kubectl patch agentset claude-travel --type=json -p='[
  {"op":"add","path":"/spec/agents/2/container/env/-",
   "value":{"name":"EXTRA_SKILLS","value":"price-comparison"}}]'

    /spec/agents/2 is hotels, the third entry in the manifest. Once the hotels pods roll, Kynomesh sees that its card changed and restarts the supervisor. Its ask_hotels tool now lists the new skill. Check the supervisor pod's age to see the restart:

    kubectl get pods

    [!NOTE] driftReload is off by default because it restarts pods automatically. Enable it for the agents that depend on other agents' cards, as this manifest does.

    Clean Up¶

    make delete

    Make It Your Own¶

    • Write good cards. The supervisor routes by each worker's description and skills, so describe what your workers do and when to use them.
    • Use any workers. They do not need to be Claude agents or share the supervisor's image. Anything that serves an AgentCard over A2A and is in the AgentSet is discovered the same way, including LangGraph agents. The mixed-fleet example does exactly that.
    • Keep the lock-down. Generated tools are added to allowed_tools automatically. Do not re-enable built-in tools to make the supervisor "more capable".
    • Know what discovery covers. The worker list is read at startup, and Kynomesh restarts the supervisor when workers are added or removed, or when driftReload detects a changed card.

    Troubleshooting¶

    • The supervisor says it has no workers: check kubectl get pods. Workers that are not running or whose cards cannot be fetched are skipped, and the supervisor logs a warning for each.
    • A new worker is not picked up: check that it is in the AgentSet and that the supervisor pod restarted after you applied the manifest.
    • A changed card is not picked up: check that driftReload is enabled.
    • A worker error appears in the answer: the supervisor reports a failed worker instead of crashing. Check that worker's logs with kubectl logs.
    • no compatible transports found: every AgentInterface in each agent's card needs protocol_version set.

    You have now run a single Claude agent and a supervisor that discovers its workers. To mix frameworks in one AgentSet, see the mixed-fleet example, and for other ways to wire agents together, see the AgentSet patterns.
